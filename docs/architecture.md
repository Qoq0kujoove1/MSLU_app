# Архитектура MSLU App

Документ описывает техническую архитектуру клиент-серверного приложения MSLU App, механизмы управления сессиями, интеграционные сценарии (отчисление, перевод группы), безопасность, хранение данных и систему мониторинга (QoS / SLA). Пользовательское описание возможностей — в [README.md](../README.md).

## Стек

- **Frontend:** Flutter, BLoC, SQLite (`sqflite`/`drift`)
- **Backend:** Python/Node.js, PostgreSQL, JWT
- **Infra:** Docker, Docker Compose, Nginx

## 1. Управление авторизацией и жизненный цикл сессии
### 1.1. Запуск или обращение при завершении сессии
- **Истечение Access Token**: Access Token имеет короткий срок жизни (например, 15–60 минут). При отправке любого запроса с истекшим токеном бэкенд возвращает статус 401 Unauthorized.

- **Фоновое обновление (Silent Refresh)**: Сетевой интерцептор (NetworkClient) на мобильном клиенте перехватывает ответ 401, берет Refresh Token из защищенного хранилища (Keystore/Keychain) и выполняет фоновый запрос /api/v1/auth/refresh. После получения новой пары токенов исходный запрос повторяется без отображения экрана входа для пользователя.

- **Завершение Refresh Token (30 дней)**: Если пользователем не производились обращения более 30 дней и Refresh Token истек, клиент удаляет токены из хранилища и перенаправляет пользователя на экран авторизации.

### 1.2. Блокировка аккаунта и отчисление студента
- **Синхронизация бэкенда**: При плановом опросе или попытке фоновой синхронизации сервис авторизации проверяет статус учетной записи через LDAP/LK МГЛУ.

- **Аннулирование сессии**: Если учетная запись заблокирована/деактивирована, бэкенд мгновенно помещает текущий Refresh Token и Session ID пользователя в Blacklist в Redis и меняет статус пользователя в PostgreSQL на DEACTIVATED.

- **Реакция клиента**: Бэкенд возвращает статус 403 Forbidden с кодом ошибки ACCOUNT_DISABLED. Клиент выполняет моментальную очистку локальной базы данных (SQLite), удаляет ключи из Keystore/Keychain и сбрасывает состояние системы до экрана авторизации с информационным сообщением.

### 1.3. Где хранятся токены на стороне сервера?
- **Access Token**: Содержит подпись HMAC-SHA256 или RS256 и является Stateless (сервер проверяет его подлинность по публичному/приватному ключу без обращения к БД).

- **Refresh Token & Session State**: Хранятся в памяти Redis Key-Value Store с TTL (Time-To-Live) 30 дней.

- **Структура записи**: session:{user_id}:{device_id} $\rightarrow$ {refresh_token_hash, created_at, last_active_ip, device_info, is_revoked}.

- Хранение в Redis позволяет моментально отзывать сессии конкретного устройства (Revocation List), завершать все сессии при смене пароля и проверять блокировки.

## 3. Обработка изменений академического статуса (Перевод в другую группу)

При переводе студента в другую учебную группу или изменении подгруппы (например, подгруппы по иностранному языку):

1. **Детекция изменений:** При фоновой синхронизации бэкенд сравнивает полученный от серверов МГЛУ хеш структуры профиля `group_id` / `subgroup_ids` с текущей записью в PostgreSQL.
2. **Обновление привязок:**
   * Бэкенд обновляет связку `User` $\rightarrow$ `Group_ID`.
   * Инициируется автоматический перерасчет персональной сетки расписания для данного пользователя.
3. **Очистка и каскадное обновление кэша:**
   * Сервер при следующем отклике отправляет флаг необходимости сброса кэша расписания (`"force_schedule_invalidation": true`).
   * Мобильный клиент очищает устаревшую сетку занятий из локальной БД (SQLite) и атомарно записывает новое расписание переведенной группы.
4. **Сохранность заметок и ДЗ:** Заметки к общеуниверситетским или пересекающимся предметам сохраняются. Заметки к предметам, отсутствующим в новой программе, переносятся в раздел *"Архив заметок"*, исключая потерю пользовательских данных.

## 4. Корпоративная почта студента (`@mslu.ru` / `@linguanet.ru`)

### Какая привязка и зачем нужна?
Корпоративная почта является **главным уникальным идентификатором (Primary Identity)** студента в системе. Она используется для:
* Сквозной аутентификации через SSO / LDAP вуза.
* Отправки критических системных оповещений (смена пароля, вход с нового устройства).
* Проверки принадлежащих студенту приказов, справок и ведомостей.

### Где хранится?
* **Бэкенд:** Таблица `users` в PostgreSQL (столбец `email VARCHAR UNIQUE`), защищенная шифрованием на уровне базы или поля.
* **Клиент:** В защищенном хранилище EncryptedSharedPreferences (Android) / Keychain (iOS) исключительно для отображения в профиле.

### Как используется?
* При вводе логина/почты бэкенд формирует запрос к корпоративному серверу аутентификации.
* Корпоративная почта связывает учетную запись мобильного приложения с внутренним реестром студентов МГЛУ для парсинга и адресации push-уведомлений.

## 5. Мониторинг, метрики и определение работоспособности

### Что значит «Приложение работает»?
Приложение считается полностью работоспособным, если выполняются условия **SLA (99.5% Uptime)**:
1. **Доступность API Gateway:** Ошибки уровня `5xx` составляют меньше $0.5\%$ от общего числа запросов.
2. **Стандарт генерации ответа за фиксированное время:**
   * Запросы из кэша бэкенда / локальной БД: **$< 100\text{ мс}$** (p95).
   * Запросы тяжелой синхронизации с внешними серверами МГЛУ: **$< 1500\text{ мс}$** (p95).
3. **Функционирование Offline-First:** В случае полного падения внешних серверов МГЛУ мобильное приложение сохраняет возможность открывать расписание, оценки и заметки из локальной базы данных без отображения фатальных ошибок.

### Как мы проверяем, что приложение работает?
Для контроля работоспособности используется стек **Prometheus + Grafana + OpenTelemetry + Sentry**:

#### 1. Метрики бэкенда (Собираются через Prometheus):
* **HTTP RED Metrics:**
  * *Rate:* Количество запросов в секунду (RPS).
  * *Errors:* Процент ответов с кодами `4xx` и `5xx`.
  * *Duration:* Гистограмма латентности ответов (p50, p95, p99).
* **Health Checks:** Эндпоинт `/healthz` регулярно опрашивается оркестратором и проверяет соединения с PostgreSQL, Redis и доступность парсера МГЛУ.
* **Business Metrics:** Количество успешных авторизаций, скорость доставки Push-сообщений, доля активных сессий (DAU/MAU).

#### 2. Мониторинг мобильного клиента (Телеметрия):
* **Crash Rate:** Процент сессий без сбоев (Target: $> 99.9\%$). Отслеживается через **Sentry / Firebase Crashlytics**.
* **Performance Traces:** Измерение времени холодной загрузки приложения (Cold Start $< 1.5\text{ с}$) и времени отрисовки экранов расписания ($< 100\text{ мс}$).
* **Network Failure Metrics:** Фиксация случаев, когда внешняя система МГЛУ недоступна, с автоматическим переводом клиентов в изолированный Offline-режим.

| Метрика | Целевой показатель | Инструмент контроля |
| :--- | :--- | :--- |
| **App Crash-Free Rate** | > 99.9% | Sentry / Crashlytics |
| **Backend Latency (p95)** | < 100 ms | Prometheus / Grafana |
| **Full Data Sync Time** | < 1.5 sec | OpenTelemetry |
| **Max Push Notification Delay** | < 5 sec | FCM Logs / Internal Worker |
| **Cold Start Time** | < 1.5 sec | Android Vitals / Xcode Metrics |
