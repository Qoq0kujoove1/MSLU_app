# Архитектура MSLU App

Технический документ. Описывает реализацию авторизации, хранения данных на клиенте и связанных механизмов. Пользовательское описание возможностей — в [README.md](../README.md).

## Стек

- **Frontend:** Flutter, BLoC, SQLite (`sqflite`/`drift`)
- **Backend:** Python/Node.js, PostgreSQL, JWT
- **Infra:** Docker, Docker Compose, Nginx

## 1. Авторизация

### 1.1 Токены

<img width="401" height="860" alt="Group 64" src="https://github.com/user-attachments/assets/5a8cf779-601c-45fa-9425-4017f934920a" />

| Токен | TTL | Хранение | Назначение |
|---|---|---|---|
| Access token | 15 мин | В памяти приложения (BLoC state), не персистится | Авторизация запросов к API |
| Refresh token | 30 дней | `flutter_secure_storage` (Keychain / Keystore) | Получение нового access token без повторного логина |

Refresh token используется **с ротацией**: при каждом обновлении backend выдаёт новый refresh и инвалидирует предыдущий. Попытка повторного использования уже отозванного refresh token — сигнал компрометации, сессия отзывается полностью.

### 1.2 Backend

- Пароль хранится только в виде хеша **Argon2id** (memory ≥ 19 MiB, iterations ≥ 2, parallelism 1).
- `POST /auth/login` — принимает логин/пароль, возвращает пару access + refresh.
- `POST /auth/refresh` — принимает refresh token, возвращает новую пару (ротация), инвалидирует старый refresh в БД.
- Rate limiting на попытки входа: 5 попыток / 15 минут на аккаунт или IP.
- Весь трафик — только по HTTPS.

### 1.3 Первый вход (flow)

1. Пользователь вводит логин и пароль.
2. `POST /auth/login` → backend проверяет пароль через Argon2id.
3. Backend выдаёт access + refresh токены.
4. Refresh сохраняется в `flutter_secure_storage`, access — в памяти.
5. Переход на главный экран.

### 1.4 Повторные входы (silent restore)

1. Запуск приложения → splash screen.
2. Проверка наличия refresh token в secure storage.
3. Если есть — тихий запрос `POST /auth/refresh` (без участия пользователя).
4. Backend сверяет и ротирует токен, возвращает новый access token.
5. Главный экран открывается сразу, с данными из локального кеша, пока идёт фоновое обновление.
6. Если refresh невалиден/просрочен — редирект на экран логина.

### 1.5 Работа с API (interceptor)

HTTP-interceptor (Dio) перехватывает ответы:

- Если ответ `401 Unauthorized` — приложение молча вызывает `/auth/refresh`, получает новый access token и повторяет исходный запрос.
- Если refresh тоже невалиден — session считается завершённой, пользователь переводится на экран логина.

### 1.6 Двухфакторная аутентификация (TOTP)

- Стандарт RFC 6238 (Google Authenticator / Authy), не требует платных сервисов.
- При подключении: backend генерирует secret (32 байта, base32) → QR-код (`otpauth://totp/...`) → пользователь сканирует → подтверждает первым кодом → secret сохраняется в БД в зашифрованном виде.
- При входе (если 2FA включена): после проверки пароля запрашивается 6-значный код, сверяется через `pyotp`/`speakeasy` с окном `valid_window=1` (±30 сек).
- Обязательны backup-коды (8–10 шт., одноразовые, хешируются как пароль) на случай потери устройства.
- Нагрузка на сервер незначительна — проверка TOTP это одна HMAC-SHA1 операция (микросекунды).

## 2. Локальное кеширование (offline-first)

- Токены и любые секреты — **только** в `flutter_secure_storage`, никогда в SQLite в открытом виде.
- Прикладные данные (расписание, успеваемость, ДЗ, профиль) — в SQLite, каждая запись с полем `cached_at`.
- Логика чтения: приложение сразу отдаёт то, что есть в SQLite (мгновенно, работает офлайн), параллельно уходит запрос на backend за свежими данными (stale-while-revalidate). При получении ответа — обновляется SQLite и UI.
- Фоновая очистка записей старше 30 дней (`WHERE cached_at < now() - 30 days`), чтобы база не росла бесконечно.
- Если приложение офлайн и кеш старше 30 дней — данные всё равно показываются, с пометкой давности ("обновлено N дней назад"), а не пустым экраном.

### Разделение по типу данных на клиенте

| Тип данных | Где хранится | Причина |
|---|---|---|
| Access token | Память (BLoC) | Короткоживущий, не должен переживать перезапуск |
| Refresh token | `flutter_secure_storage` | Долгоживущий секрет, требует шифрования на уровне ОС |
| Расписание / успеваемость / ДЗ | SQLite | Не секретные данные, нужен offline-доступ и быстрый локальный запрос |

## 3. Домашний экран — источники данных

Домашний экран — агрегатор, не делает отдельных тяжёлых запросов к backend:

- Ближайшая/текущая пара — вычисляется на клиенте сравнением текущего времени с расписанием, уже загруженным в SQLite.
- Средний балл, счётчик ДЗ — читаются из тех же локальных таблиц, что и полноценные разделы «Успеваемость» и «ДЗ».
- Обновление данных — при обычной фоновой синхронизации кеша или по push-уведомлению о конкретном изменении (новая оценка, замена пары).

- Нужна ли геолокация корпуса по конкретной паре, если в течение дня пары проходят в разных зданиях.
- Формат push-уведомлений (FCM/APNs) и то, какие события их триггерят на backend.
