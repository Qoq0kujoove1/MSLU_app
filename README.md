# MSLU App
Мобильное приложение для студентов Московского государственного лингвистического университета.

## Описание
### Основные возможности
- Расписание занятий (день/неделя/месяц)
- Успеваемость
- Профиль студента
- Локальное кэширование для быстрого доступа
### 1. Авторизация, безопасность и работа с данными
<img width="1920" height="1080" alt="D" src="https://github.com/user-attachments/assets/fe04fc1a-3785-44a6-bbf4-f59649d76861" />

Система аутентификации и управления данными спроектирована по принципу **Offline-First** с упором на безопасность и бесшовный пользовательский опыт (Seamless Login).

#### 1. Технологический стек
- **Клиент**: Flutter (Dart), BLoC для управления состоянием, SQLite (`sqflite`/`drift`) для локального кэша
- **Backend**: Python/Node.js, PostgreSQL
- **Локальное хранилище**: `flutter_secure_storage` (Keychain на iOS, Keystore на Android)

#### 2. Управление токенами (JWT)
- **Access Token**:
  - Время жизни: **15 минут**
  - Хранится **только в оперативной памяти** приложения (состояние BLoC), не персистится на диск
  - Используется в заголовке `Authorization: Bearer <token>` для всех защищённых запросов к API
  
- **Refresh Token**:
  - Время жизни: **30 дней**
  - Хранится в защищённом хранилище ОС (`flutter_secure_storage`)
  - **Ротация**: при каждом вызове `/auth/refresh` старый токен немедленно инвалидируется в базе данных, выдаётся новый (защита от replay attacks)

#### 3. Безопасность и хранение данных
- **Пароли**: Никогда не хранятся в открытом виде. Хеширование выполняется алгоритмом **Argon2id** (параметры: memory ≥19 MiB, iterations ≥2)
- **Транспорт**: Всё взаимодействие между клиентом и сервером происходит строго по **HTTPS**
- **Защита от перебора (Rate Limiting)**: На эндпоинте `/auth/login` установлено ограничение: максимум 5 попыток входа с одного IP/устройства за 15 минут

#### 4. API-эндпоинты аутентификации
- **`POST /auth/login`**: Принимает логин и пароль. При успешной валидации возвращает пару `access_token` + `refresh_token`
- **`POST /auth/refresh`**: Принимает `refresh_token`, возвращает новую пару токенов (ротация). Старый `refresh_token` немедленно инвалидируется в базе данных

#### 5. Пользовательские сценарии (User Flow)

**Первый вход:**
1. Пользователь вводит логин/пароль на экране авторизации
2. Backend проверяет учётные данные (сверка хэша Argon2id)
3. При успехе сервер выдаёт пару токенов
4. `refresh_token` сохраняется в `flutter_secure_storage`, `access_token` загружается в память (BLoC state)
5. Переход на главный экран приложения

**Повторные входы (Авто-вход):**
1. При запуске приложения отображается Splash Screen
2. Клиент проверяет наличие `refresh_token` в защищённом хранилище
3. Если токен найден, выполняется тихий фоновый запрос на `/auth/refresh`
4. Полученный новый `access_token` загружается в память
5. Переход на главный экран (данные сразу отображаются из локального SQLite-кэша, пока идёт фоновое обновление)

#### 6. Сетевой слой и перехватчики (Interceptors)
- Клиент использует HTTP-клиент (`Dio`) с настроенным интерсептором
- Если любой запрос к API возвращает `401 Unauthorized`, интерсептор **автоматически**:
  1. Приостанавливает очередь запросов
  2. Выполняет запрос на `/auth/refresh`
  3. Получает новый `access_token`
  4. Подставляет его в заголовок исходного запроса
  5. Повторяет запрос (для пользователя процесс полностью незаметен)
- Если `refresh_token` также невалиден (истёк 30-дневный срок или устройство отозвано), происходит очистка хранилища и редирект на экран логина

#### 7. Офлайн-первый подход (Offline-First & Кэширование)
- Прикладные данные (расписание, успеваемость, профиль) хранятся в локальной базе **SQLite** с меткой времени `cached_at`
- **Stale-While-Revalidate**: UI мгновенно отображает данные из локального кэша. Параллельно в фоне идёт запрос к серверу. Если данные изменились, кэш обновляется, и UI перерисовывается
- **Очистка**: Записи в кэше старше 30 дней периодически удаляются фоновыми задачами для экономии места на устройстве

#### 8. Двухфакторная аутентификация (2FA) через TOTP
Для повышения уровня защиты учетных записей предусмотрена поддержка двухфакторной аутентификации на основе алгоритма TOTP (Time-based One-Time Password, RFC 6238).

- **Реализация**: Используются легковесные и проверенные библиотеки: `pyotp` (для Python) или `speakeasy`/`otplib` (для Node.js). Они бесплатны и не имеют тяжелых внешних зависимостей.
- **Производительность (Нагрузка)**: Практически нулевая. 
  - Проверка TOTP-кода — это одна операция HMAC-SHA1, занимающая микросекунды (сервер легко обрабатывает десятки тысяч проверок в секунду даже на 1 vCPU).
  - Единственная дополнительная операция — один `SELECT` из базы данных для получения `secret`-ключа пользователя, что и так происходит в процессе стандартного логина.
  - Генерация QR-кода для привязки аутентификатора — разовая операция, не влияющая на производительность при обычных входах.
- **Отказ от SMS**: Намеренно исключена SMS-верификация. Она требует платных интеграций с провайдерами (тарификация за каждое сообщение) и менее безопасна из-за уязвимости к SIM-swap атакам. TOTP является оптимальным, бесплатным и современным выбором для данного проекта.
### 2. Возможности домашнего экрана
Макет домашнего экрана

#### 1. Структура экрана

##### 1.1. Шапка (Header)
- **Аватар + Имя**: Данные из профиля пользователя. Тап по аватару/имени открывает полный экран профиля.
- **Группа**: Статичное поле из профиля (например, «ИИН 1-24-1»).
- **Колокольчик (Уведомления)**: Иконка с бейдж-счётчиком непрочитанных уведомлений (замена пары, отмена, новая оценка, домашнее задание).
- **Иконка чата**: Переход в раздел сообщений. Если функционал чатов не входит в MVP, ведёт на заглушку или скрывается.

##### 1.2. Индикатор учебной недели
- **Отображение**: «Неделя: Числитель» или «Неделя: Знаменатель» (стандартная для вузов система чередования расписания).
- **Иконка обновления**: Принудительная синхронизация расписания с сервером (на случай, если автообновление не сработало).
- **Логика расчёта**: Вычисляется на backend или локально от даты начала семестра. Не требует отдельного запроса при каждом открытии экрана.

##### 1.3. Дата и локация
- **Дата и день недели**: Текущая дата (например, «Сегодня: 16 апреля, Четверг»).
- **Геометка**: Корпус, где проходят занятия (например, «Остоженка д. 36»). Если у вуза несколько корпусов и они меняются в течение дня, показывается либо общая локация на день, либо меняется по текущей паре.

##### 1.4. Виджет «Идёт сейчас» / «Следующая пара»
- **Условие отображения**: 
  - Если прямо сейчас идёт пара (сравнение текущего времени с расписанием) — показывается блок «Идёт сейчас».
  - Если пара ещё не началась — показывается «Следующая пара через N минут».
  - Если пар сегодня нет — виджет скрывается или показывает «Сегодня пар нет».
- **Содержимое блока «Идёт сейчас»**:
  - Предмет
  - Тип занятия (семинар/лекция/практика — с иконкой-маркером)
  - Преподаватель
  - Номер аудитории
- **Действие**: Тап по карточке открывает детали пары (полное описание, материалы).

##### 1.5. Список пар на сегодня
- **Отображение**: Хронологический список оставшихся пар (после текущей).
- **Карточка пары**: Время начала, предмет, тип занятия, преподаватель, аудитория.
- **Пустое состояние**: Если пар на сегодня больше не осталось — отображается сообщение «На сегодня пар больше нет 🎉».
- **Действие**: Тап по карточке открывает детали пары.

##### 1.6. Виджет «Успеваемость» (нижняя карточка)
- **Средний балл**: Агрегированное значение из раздела успеваемости.
- **Обновление**: При появлении новой оценки — через push-уведомление от backend или пересчёт при фоновой синхронизации кэша.
- **Действие**: Тап по виджету открывает полный раздел успеваемости (по предметам).

##### 1.7. Виджет «ДЗ» (Домашние задания)
- **Счётчик**: Количество несданных/предстоящих домашних заданий.
- **Цветовая индикация срочности**:
  - 🟢 Зелёный: дедлайн более чем через 3 дня
  - 🟡 Жёлтый: дедлайн через 1–2 дня
  - 🔴 Красный: дедлайн сегодня/завтра
- **Действие**: Тап открывает список домашних заданий.

#### 2. Нижняя навигация (Bottom Navigation Bar)

Четыре основные вкладки:
1. 🏠 **Дом** (текущий экран, активный)
2. 📅 **Календарь** (полное расписание)
3. 📊 **Аналитика** (успеваемость как отдельный полноценный раздел)
4. 👤 **Профиль**

**Важно**: Раздел «ДЗ» отсутствует в нижнем меню. Домашние задания доступны только с домашнего экрана или как подраздел расписания/успеваемости. Это архитектурное решение должно быть явно зафиксировано.

#### 3. Техническая реализация

##### 3.1. Источники данных
- **Все виджеты**: Данные агрегируются из локального SQLite-кэша (расписание, успеваемость, ДЗ).
- **Отсутствие тяжелых запросов**: При каждом открытии экрана не выполняются отдельные запросы к серверу. Данные обновляются фоновыми задачами или через push-уведомления.

##### 3.2. Клиентская логика
- **«Идёт сейчас» / «Следующая пара»**: Чисто клиентская логика (сравнение текущего времени с данными из кэша). Не требует запроса к серверу.
- **Обновление счётчиков**: Счётчик ДЗ и средний балл обновляются либо через push-уведомление от backend при изменении данных, либо при пересчёте во время обычной фоновой синхронизации кэша.

##### 3.3. Состояния экрана (для UX/UI)
1. **Skeleton Loading**: Мерцающие блоки на месте всех виджетов (первые 0.5–1 секунды, пока читается SQLite).
2. **Offline Mode**: Баннер «Нет подключения к интернету. Показаны сохранённые данные» (виджеты работают из кэша).
3. **Empty State**: Дружелюбные сообщения для случаев, когда нет пар, оценок или ДЗ.
